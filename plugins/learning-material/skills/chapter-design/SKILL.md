# 단원 기획서 작성

교재 집필자가 어떤 내용을 어떤 흐름과 깊이로 담을지 알 수 있는 간략한 기획서를 만든다. 이론은 핵심 개념과 학습 흐름, 미션과 프로젝트는 핵심 수행과 결과물을 중심으로 쓴다. 구체적인 예제, 실습 문제와 세부 수업 구성은 교재 제작 단계에 맡긴다.

## 입력과 템플릿

과정 컨텍스트와 작성 범위는 실행할 때 받는다. 특정 과정의 기술 스택, 시수, 장비, 운영 방식, 디렉터리 구조를 기본값으로 가정하지 않는다. 작업 프로젝트의 지침과 기존 합의는 해당 범위에 적용한다.

단원 유형에 맞는 템플릿을 읽는다. 사용자가 템플릿을 갱신했다고 알리면 최신 파일을 다시 읽는다. 경로는 이 SKILL.md의 위치를 기준으로 해석한다.

- [이론 템플릿](assets/template_단원_기획_이론.md)
- [미션 템플릿](assets/template_단원_기획_미션.md)
- [프로젝트 템플릿](assets/template_단원_기획_프로젝트.md)

`assets/`는 형식의 기준이며 결과물 저장 위치가 아니다. 템플릿 원본을 수정하지 않고 사용자가 지정한 경로에 기획서를 저장한다.

## 작성 수준과 문체

- 쉬운 용어와 짧은 합니다체 문장으로 쓴다. 기술 용어는 억지로 번역하지 않는다. AI처럼 보편적인 약어는 그대로 쓰고, 흔하지 않은 약어는 첫 등장에만 `약어(Full Spelling)`로 쓴다. 새 마크다운에는 미들닷(U+00B7)을 사용하지 않는다.
- 학습 목표는 수행 가능한 행동을 중심으로 1–2문장으로 쓴다. 본문은 의미 있는 개념이나 수행 묶음별로 짧은 불릿을 사용한다. 개념 이름만 나열하지 않고 무엇을 배우거나 수행하며 어디까지 다룰지 드러낸다.
- 앞뒤 학습의 연결은 순서만으로 이해하기 어려운 지점에 짧게 설명한다. 별도의 도입 이야기, 항목별 필요성 설명, 강사 대본을 형식적으로 채우지 않는다.
- 단원 총 시수는 입력에서 확인된 값만 적는다. 항목별 시간과 비율, 강의와 실습을 구분한 시간표는 작성하지 않는다. 실습 시간 상한이나 연속 강의 시간에 맞춘 항목 분할도 기획 요건으로 두지 않는다.
- 구체적인 예제와 실습 문제, 함수명, 파일별 코드 구조, API 필드, 설치 절차, 세부 채점표는 새로 정하지 않는다. 학습 목표나 기존 합의상 꼭 필요한 제약은 유지한다.
- 합의된 내용과 제안을 구분한다. 미확인 장비 기능, 코드 제공 여부, 준비 주체, 비용을 확정된 사실로 쓰지 않는다.
- 도움 설명, 작성 예시, 빈 항목과 자리표시자는 결과물에서 제거한다. 제작 참고 사항은 중요한 내용이 있을 때만 작성하고, 없으면 섹션을 생략한다.

## 워크플로우

### 1. 컨텍스트와 작성 범위 확인

커리큘럼, 훈련 대상과 선수 지식, 훈련 목표, 기존 합의 자료를 읽는다. 작성할 교과목과 단원, 유형(이론/미션/프로젝트), 총 시수, 저장 경로를 확인한다. 이미 제공된 정보는 다시 묻지 않고, 작성에 필요한 정보만 추가로 받는다. 입력에 없는 단원 구성이나 유형은 임의 확정하지 않는다.

과정 목표, 선수 단원과 후속 단원의 연결, 중요한 기술이나 환경 제약을 파악한다. 과거 자료와 최신 입력이 충돌하면 관련 부분을 보여 주고 확인한다. 기존 파일을 수정하는 경우 현재 작업본을 읽고, 보관본과 구별해 지정된 범위만 수정한다.

여러 단원은 단원별 파일로 작성한다. 파일명은 사용자가 정한 규칙이나 대상 폴더의 관례를 따르고, 둘 다 없으면 단원 순서와 제목을 사용한다.

### 2. 핵심 결정 인터뷰

`$grill-with-docs`와 연결된 `grilling`, `domain-modeling`의 지침을 읽고 적용한다. Skill 호출 도구가 없으면 각 SKILL.md를 직접 읽어 수행한다. 필수 스킬이 없다면 발견 가능한 경로를 확인하고, 끝내 찾지 못하면 인터뷰와 작성을 중단하고 필요한 스킬을 안내한다. 사용하지 않은 스킬을 사용했다고 보고하지 않는다.

인터뷰에서는 핵심 범위, 학습 흐름, 중요한 제약 중 방향이 갈리는 사항만 질문한다. 원자료에 답이 있는 항목은 반복 확인하지 않는다. 프로젝트에 질문 방식이 정해져 있으면 따르고, 그렇지 않으면 인터뷰 스킬의 방식을 따른다.

- 이론은 핵심 개념의 선정과 순서, 다룰 깊이, 중요한 적용 목적을 정한다.
- 미션과 프로젝트는 선행 학습으로 수행할 핵심 내용과 결과물을 정하고, 필수, 기본, 심화의 범위를 구분한다.
- 제공 자료나 환경이 학습자가 직접 수행할 범위 또는 기획의 실현 가능성을 바꿀 때만 그 경계를 확인한다. 세부 리소스 목록, 파일 선정, 설치 절차, 구체적인 소재와 문제 구성은 필수 결정 사항으로 두지 않는다.
- 총 시수와 학습자 수준에 비해 범위가 과도하거나 부족한지 살핀다. 시수를 채우려고 내용이나 반복 활동을 추가하지 않는다. 시수 변경은 사용자가 허용한 범위에서만 제안하며, 기획상 판단을 실제 소요 시간 검증으로 표현하지 않는다.
- 용어와 중요한 선택 이유는 `domain-modeling`에 따라 대상 프로젝트의 관례에 맞게 기록한다. 일반적인 작성 메모를 모두 용어집이나 ADR로 만들지 않는다.

핵심 범위와 흐름, 중요한 제약이 정해지면 인터뷰를 마친다. 교재 제작자가 선택할 수 있는 세부 사항으로 질문을 확장하지 않는다. 합의 내용과 중요한 유보 사항을 짧게 정리하고 사용자 확인을 받은 뒤 작성한다. 사용자가 합의 내용을 제공하고 그에 따라 작성을 요청했다면 다시 확인하지 않는다. 침묵을 동의로 해석하지 않는다.

### 3. 단원 기획서 초안 작성

유형별 템플릿에 합의한 내용을 채운다. 인터뷰 기록과 검토 이력은 본문에 넣지 않는다.

**이론**

개념 묶음을 학습 순서대로 배치하고, 각 묶음에서 다룰 핵심 개념과 학습 방향을 짧게 설명한다. 강의와 실습을 별도 항목으로 나눌 필요는 없다. 실습이 중요한 지점에는 어떤 개념을 적용하거나 확인할지만 적는다. 기본 범위는 별도 표시 없이 쓰고, 선택 확장이 필요할 때만 심화로 구분하며 기본 학습의 전제로 두지 않는다.

작성 깊이의 예시:

> **함수로 처리 과정 나누기**
> - 매개변수와 반환값, 변수의 범위를 다룹니다.
> - 반복되는 처리 과정을 함수로 나누고, 여러 함수를 연결해 프로그램을 구성합니다.

**미션과 프로젝트**

학습자가 무엇을 수행하고 어떤 결과물을 만드는지 짧게 설명하고, 핵심 수행을 흐름에 따라 불릿으로 쓴다. 각 항목에는 `[필수]`, `[기본]`, `[심화]` 중 하나를 반드시 표시한다.

- 필수: 기본 범위 안의 최소 달성 요건이다. 수행에 어려움이 있어도 상세 가이드나 튜토리얼의 도움을 받아 달성해야 한다.
- 기본: 모든 수강생이 수행하는 공통 요구사항이다. 필수로 표시한 항목도 기본 수행 범위에 포함되므로 중복해서 쓰지 않는다.
- 심화: 학습 성취도가 높은 수강생을 위한 선택 확장이다. 필수나 기본 수행의 전제로 두지 않는다.

특정 소재의 구현 명세보다 선행 학습을 어떻게 조합하고 적용하는지 드러낸다. 우선순위는 명시하되, 항목마다 필요성과 상세 설명을 반복하지 않는다.

**제작 참고 사항**

리소스, 소재, 평가 유의점, 환경 제약을 별도 필수 섹션으로 나누지 않고 이곳에 통합한다. 본문에 없는 중요한 내용만 적는다. 예를 들어 제공 모델을 활용하는 범위, 학습자가 혼동하기 쉬운 개념, 소재 선정의 핵심 조건, 결과물에서 반드시 확인할 역량이 해당한다. 평가 항목 수를 채우거나 세부 채점 기준을 만들지 않는다.

기획 의도에 영향을 주는 제약은 남기되, 교재 제작 단계의 모든 미결정 사항을 나열하지 않는다. 중요한 미확인 조건이 있으면 그 상태를 짧게 밝힌다.

### 4. 별도 에이전트 검토

초안을 최종 경로에 저장하기 전에 반드시 별도 에이전트에게 검토를 맡긴다. 초안은 전달문이나 임시 경로로 제공한다. 검토자에게 사용자 입력, 관련 원자료, 인터뷰 합의, 선택한 템플릿, 이 스킬을 제공하고 다음을 확인하게 한다.

- 학습자 수준과 목표, 선수 학습에 맞는 핵심 내용이 담겼는가?
- 무엇을 어떤 흐름과 깊이로 다룰지 이해할 수 있으며, 중요한 내용이 누락되거나 모순되지 않는가?
- 미션과 프로젝트의 각 핵심 수행 항목에 필수, 기본, 심화 중 하나가 표시되어 있는가? 필수는 기본 범위의 최소 달성 요건이며, 심화를 필수나 기본의 전제로 두지 않았는가?
- 미션과 프로젝트의 핵심 수행과 결과물이 분명하며, 제공 범위가 중요한 경우 직접 수행할 범위와 구별되는가?
- 합의되지 않은 내용을 확정하거나, 기획에 불필요한 상세 시간표와 문제 설계까지 확장하지 않았는가?
- 제작 참고 사항에는 중요한 제약과 유의점만 남겼는가? 선택 항목이나 제작 단계의 세부 사항이 생략되었다는 이유로 미완성으로 판단하지 않는다.
- 여러 단원 사이에 불필요한 중복, 선수 지식 누락, 모순이 없는가?

검토자는 초안을 직접 수정하지 않고 문제 위치, 근거, 최소 수정안을 반환한다. 작성자는 타당한 지적을 반영한다. 핵심 범위나 중요한 제약을 바꾸는 결정이 필요할 때만 인터뷰로 돌아간다. 별도 에이전트를 사용할 수 없다면 제약을 알리고 대체 검토 방식을 사용자와 정한다. 자체 재독을 별도 검토로 보고하지 않는다.

### 5. 최종 저장

검토를 반영한 파일을 사용자 지정 경로에 저장한다. 링크, 입력과 총 시수의 일치, 남은 도움 설명이나 자리표시자, 새 미들닷을 확인한다. 기존 문서 수정 시 관련 없는 내용과 메타데이터를 보존하고, 보관본 등 범위 밖의 파일은 변경하지 않는다.

완료 시 저장한 파일 경로, 검토 수행 여부, 남은 중요한 제작 확인사항만 짧게 알린다. 기획서 검토를 실제 코드, 장비 동작이나 학습 소요 시간의 검증으로 표현하지 않는다.
